E01 · Translate arrow functions without guessing

Review the core ideaRead the full explanation

This is a standalone TypeScript drill. Write each function in both expression-body and block-body form. First predict the results of triple(4), label("Tea"), and makeItem("Tea"). Then explain every pair of parentheses and braces out loud.

  • Return 12 from triple(4).
  • Return "Item: Tea" from label("Tea").
  • Return an object with name "Tea" from makeItem("Tea").
  • Use no any types.
Starter code
const triple = (n: number) => { n * 3; };
const label = (name: string) => { return "Item: " + name; };
const makeItem = (name: string) => { name: name };
Hint 1

A block body needs an explicit return when a result is required.

Hint 2

An object expression begins with a brace, so wrap the object in parentheses in an expression body.

Hint 3

Compare n => n * 3 with n => { return n * 3; }.

Reference answer and explanation
// Standalone TypeScript.
const triple = (n: number) => n * 3;
const tripleBlock = (n: number) => { return n * 3; };
const label = (name: string) => "Item: " + name;
const labelBlock = (name: string) => { return "Item: " + name; };
const makeItem = (name: string) => ({ name });
const makeItemBlock = (name: string) => { return { name }; };
console.log(triple(4), label("Tea"), makeItem("Tea"));

The body after => is either one expression or a statement block. An expression body returns its value automatically. A block executes statements and needs return to provide a value. Without return, triple originally produced undefined.

In the original makeItem, the braces start a block and name: is parsed as a label, not an object property. Parentheses make ({ name }) an object expression. The shorter property name form means { name: name }.

Test the behavior

  • The three printed values are 12, "Item: Tea", and { name: "Tea" }.
  • Change the input to 0 and the empty string; the functions still return values.
  • Rewrite all three without looking, then compare expression and block results.

Hint 2

// Component-body fragment; Text and View are imported.
const items = [{ id: "a", name: "Tea" }, { id: "b", name: "Soup" }];
const rows = items.map(item => (
  <Text key={item.id}>{item.name}</Text>
));

// Equivalent map expression, used instead of the one above:

map calls the callback for each present array element and gathers the returned values into a new array. Here the input elements are data objects; the returned values are React elements. The original callback returned undefined, so it supplied no text elements to display.

The outer {rows} inserts the array into JSX. key helps React match siblings across changes. It belongs on the outermost element returned by this map, and a data ID is more stable than a changing position or a random number.

E03 · Make a counter update through React

Build a complete App.tsx counter. The count starts at zero, Add increments once, Add three increments three times, and Reset sets zero. Explain why changing a local variable is insufficient.

  • Use state at the top level of the component.
  • Pass functions to onPress.
  • Use three queued functional updates for Add three.
Starter code
// Broken component-body fragment:
let count = 0;
const add = () => { count += 1; };
Hint 1

A local variable is recreated when the component runs, and assigning it does not schedule a render.

Hint 2

useState returns the current render value and a setter.

Hint 3

Three calls to setCount(c => c + 1) compose; three calls to setCount(count + 1) use the same captured value.

Reference answer and explanation
// Complete App.tsx.
import { useState } from 'react';
import { Button, Text, View } from 'react-native';
export default function App() {
  const [count, setCount] = useState(0);
  function addThree() {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
  }
  return (
    <View style={{ padding: 40 }}>
      <Text>{count}</Text>
      <Button title="Add" onPress={() => setCount(c => c + 1)} />
      <Button title="Add three" onPress={addThree} />
      <Button title="Reset" onPress={() => setCount(0)} />
    </View>
  );
}

React retains state between renders. Calling its setter queues an update; the next render receives the next value. The count variable in the current handler remains the current render’s snapshot.

A setter accepts either the next value or an updater function. Each updater receives the pending state after earlier queued updates. This is why three functional increments produce three additional counts. An updater should be pure: return the next value without changing external data.

Test the behavior

  • Start at 0; Add gives 1; Add three gives 4; Reset gives 0.
  • Replace the three updater calls with setCount(count + 1); from 0 they produce 1. Explain before running.
  • A log of count immediately after calling its setter still shows the current handler’s captured value.

Transfer challenge

Hint 1

The setter can accept an updater. Keep that idea and fix its returned value.

Hint 2

Square brackets construct an array. Spread copies its elements into a new array.

Hint 3

Return [...previous, item] with an expression body, or use a block with return.

Reference answer and explanation
// Component-body fragment; useState is imported.
type MenuItem = { name: string; popular: boolean };
const initialMenu: MenuItem[] = [{ name: "Tea", popular: false }];
const [menu, setMenu] = useState(initialMenu);

  setMenu(previous => [...previous, item]);

E05 · Update one object and remove another

Write two handlers inside a component that stores Task[] in state. toggleTask(id) changes only the matching task’s done value. removeTask(id) deletes only that task. The IDs are unique.

  • Return new arrays.
  • Copy the changed object instead of mutating it.
  • Keep IDs stable.
  • Do nothing harmful when an ID is absent.
Starter code
type Task = { id: string; title: string; done: boolean };
const [tasks, setTasks] = useState<Task[]>([
  { id: "t1", title: "Read", done: false },
  { id: "t2", title: "Practice", done: true },
]);
// Write toggleTask and removeTask here.
Hint 1

map preserves a one-for-one relationship; filter selects which elements remain.

Hint 2

For the matching task return { ...task, done: !task.done }.

Hint 3

The filter callback should return true for tasks to keep.

Reference answer and explanation
// Component-body fragment; useState is imported and tasks exist.
function toggleTask(id: string) {
  setTasks(previous => previous.map(task =>
    task.id === id ? { ...task, done: !task.done } : task
  ));
}
function removeTask(id: string) {
  setTasks(previous => previous.filter(task => task.id !== id));
}

An immutable edit copies each level that changes: the array and the matching task object. Unchanged task objects may retain their references because their values are unchanged. [...previous] followed by next[0].done = true would still mutate the shared first object.

filter keeps elements whose predicate is true. To remove t1, keep tasks with task.id !== "t1". map transforms elements; it does not remove them just because a callback returns undefined.

Test the behavior

  • Toggle t1: t1 becomes true and t2 remains true. Toggle t1 again: it returns to false.
  • Remove t2: only t1 remains. Removing an unknown ID leaves the displayed data unchanged.
  • Save the old t1 object in a standalone test and confirm its done field did not change.

Hint 2

Reference answer and explanation
// Complete App.tsx.
import { useState } from 'react';
import { Button, Text, TextInput, View } from 'react-native';
export default function App() {
  const [name, setName] = useState('');
  return (
    <View style={{ padding: 40 }}>
      <TextInput accessibilityLabel="Your name" value={name}
        onChangeText={setName}
        style={{ borderWidth: 1, padding: 12 }} />

}
export default function App() {
  // Own names and pass an add handler to Composer.
}
Hint 1

The type is (name: string) => void. That describes the callback; it does not execute it.

Hint 2

The parent passes onAdd={addName}. The child later calls onAdd(cleanName) in a handler.

Hint 3

Props travel down; an event invokes a function supplied from above. The child does not directly write the parent’s state.

Reference answer and explanation
// Complete App.tsx. The names below are append-only; a single Text displays them.
import { useState } from 'react';
import { Button, Text, TextInput, View } from 'react-native';
type ComposerProps = { onAdd: (name: string) => void };
function Composer({ onAdd }: ComposerProps) {
  const [draft, setDraft] = useState('');
  function submit() {
    const name = draft.trim();
    if (!name) return;
    onAdd(name);
    setDraft('');
  }
  return (
    <View>
      <TextInput accessibilityLabel="New name" value={draft}
        onChangeText={setDraft} style={{ borderWidth: 1, padding: 12 }} />
      <Button title="Add" onPress={submit} disabled={!draft.trim()} />
    </View>
  );
}
export default function App() {
  const [names, setNames] = useState<string[]>([]);
  function addName(name: string) {
    setNames(previous => [...previous, name]);
  }
  return (
    <View style={{ padding: 40 }}>
      <Composer onAdd={addName} />
      <Text>{names.length ? names.join(', ') : 'No names yet'}</Text>
    </View>
  );
}

There are two pieces of state with different owners. The draft is used only inside the form, so it stays there. The submitted names are needed by the parent display, so they live in App. If two siblings later need the same draft, move it to their nearest common ancestor.

onAdd is a prop containing a function value. Calling it reports an action to the parent’s handler. This does not reverse the direction of props: the parent still supplies both data and callbacks downward, and owns the state update.

Test the behavior

  • Type two names and submit each. Both appear in order.
  • Submitting spaces adds nothing.
  • Explain the path from the press, through submit and onAdd, to setNames and the next render.

Transfer challenge

Inference is strongest when a value or surrounding context gives TypeScript useful evidence. A typed initial array, such as const initial: MenuItem[] = [], lets useState(initial) infer the same type. For an empty literal or null, an explicit type expresses the later states you intend.

TypeScript checks code before execution; types do not validate unknown network responses at runtime. The compiler can catch setTitle(42), but a type annotation alone cannot guarantee that downloaded JSON has the promised shape.

Reference answer and explanation
// Complete App.tsx for a standard Expo React Native TypeScript project or Snack.
// Original practice solution. Rebuild from the requirements before reading it.
import { useState } from 'react';
import {
  Button, Pressable, ScrollView, StyleSheet,
  Switch, Text, TextInput, View,
} from 'react-native';

type MenuDraft = { name: string; popular: boolean };
export type MenuItem = MenuDraft & { id: string };
const initialMenu: MenuItem[] = [
  { id: '1', name: 'Rice bowl', popular: true },
  { id: '2', name: 'Fruit cup', popular: false },
];

type ComposerProps = { onAdd: (draft: MenuDraft) => void };
function Composer({ onAdd }: ComposerProps) {
  const [name, setName] = useState('');
  const [popular, setPopular] = useState(false);
  const cleanName = name.trim();
  function submit() {
    if (cleanName.length === 0) return;
    onAdd({ name: cleanName, popular });
    setName('');
    setPopular(false);
  }
  return (
    <View style={styles.composer}>
      <TextInput
        accessibilityLabel="New menu item name"
        placeholder="New menu item"
        value={name}
        onChangeText={setName}
        style={styles.input}
      />
      <View style={styles.row}>
        <Text>Popular</Text>
        <Switch
          accessibilityLabel="Mark new item popular"
          value={popular}
          onValueChange={setPopular}
        />
      </View>
      <Button title="Add item" disabled={!cleanName} onPress={submit} />
    </View>
  );
}

type CardProps = {
  item: MenuItem;
  onToggle: (id: string) => void;
  onRemove: (id: string) => void;
};
function ItemCard({ item, onToggle, onRemove }: CardProps) {
  return (
    <View style={styles.card}>
      <Text style={styles.itemName}>{item.name}</Text>
      <Text>{item.popular ? 'Popular choice' : 'Regular choice'}</Text>
      <View style={styles.actions}>
        <Pressable
          accessibilityRole="button"
          accessibilityLabel={`Toggle popularity of ${item.name}`}
          onPress={() => onToggle(item.id)}
          style={styles.action}
        >
          <Text>Toggle popular</Text>
        </Pressable>
        <Pressable
          accessibilityRole="button"
          accessibilityLabel={`Remove ${item.name}`}
          onPress={() => onRemove(item.id)}
          style={styles.action}
        >
          <Text>Remove</Text>
        </Pressable>
      </View>
    </View>
  );
}

export default function App() {
  const [menu, setMenu] = useState(initialMenu);
  const [nextId, setNextId] = useState(3);
  function addMenuItem(draft: MenuDraft) {
    const item: MenuItem = { ...draft, id: String(nextId) };
    setNextId(previous => previous + 1);
    setMenu(previous => [...previous, item]);
  }
  function togglePopular(id: string) {
    setMenu(previous => previous.map(item =>
      item.id === id ? { ...item, popular: !item.popular } : item
    ));
  }
  function removeItem(id: string) {
    setMenu(previous => previous.filter(item => item.id !== id));
  }
  return (
    <View style={styles.screen}>
      <Text style={styles.title}>Campus menu</Text>
      <Text>{menu.length} items</Text>
      <Composer onAdd={addMenuItem} />
      <ScrollView contentContainerStyle={styles.list}>
        {menu.length === 0 ? (
          <Text>No items yet. Add your first one.</Text>
        ) : null}
        {menu.map(item => (
          <ItemCard
            key={item.id}
            item={item}
            onToggle={togglePopular}
            onRemove={removeItem}
          />
        ))}
      </ScrollView>
    </View>
  );
}

E12 · Debug rendering and event mistakes

Repair the fragment and explain the order of events. Assume imports, count state, and the list are already declared. Do not fix a render-time update with useEffect; fix when the handler runs.

return (
  <View>
    <Button title="Add" onPress={setCount(count + 1)} />

Hint 1

A JSX prop expression runs while rendering. setCount(...) calls the setter immediately.

Hint 2

Logical && returns one of its operands; 0 && something evaluates to 0.

Hint 3

Assume each item has a stable id assigned when created.

Reference answer and explanation
// Component JSX fragment; count, setCount, and items already exist.
return (
  <View>
    <Button title="Add" onPress={() => setCount(c => c + 1)} />
    {count > 0 ? <Text>There are items</Text> : null}
    {items.map(item => <Text key={item.id}>{item.name}</Text>)}
  </View>
);

onPress expects a function that React Native can call later. Passing the result of setCount invokes the update during render and supplies no useful handler. Wrapping the call defers it until the press. A named handler passed as onPress={handleAdd} works too.

E13 · Run one interval and clean it up

Create a seconds counter that runs while running is true and pauses when false. This covers Lecture 5a. Use an effect to manage one interval and clean it up. Predict what happens after repeatedly pausing and restarting.

  • Call hooks unconditionally at the top level.
  • Create the interval only while running.
  • Clear the interval when running changes or the component unmounts.
  • Use a functional setter inside the interval.
Starter code
// Component-body starting point:
const [seconds, setSeconds] = useState(0);
const [running, setRunning] = useState(false);
// Add an effect and Start/Pause button.
Hint 1

The effect depends on running, because that value determines whether an interval exists.

Hint 2

The cleanup must return a function: return () => clearInterval(id).

Hint 3

The interval callback uses setSeconds(s => s + 1), so it does not need to capture seconds.

Reference answer and explanation
// Complete App.tsx.
import { useEffect, useState } from 'react';
import { Button, Text, View } from 'react-native';
export default function App() {
  const [seconds, setSeconds] = useState(0);
  const [running, setRunning] = useState(false);
  useEffect(() => {
    if (!running) return;
    const id = setInterval(() => setSeconds(s => s + 1), 1000);
    return () => clearInterval(id);
  }, [running]);
  return (
    <View style={{ padding: 40 }}>
      <Text>{seconds} seconds</Text>
      <Button title={running ? 'Pause' : 'Start'}
        onPress={() => setRunning(value => !value)} />
      <Button title="Reset" onPress={() => setSeconds(0)} />
    </View>
  );
}

An effect synchronizes React with a system outside rendering: here a timer. When running changes, React cleans up the previous effect before running the next setup. When the component is removed, it cleans up again. Without cleanup, repeated starts can leave multiple intervals running.

The updater receives fresh pending state, avoiding a callback that keeps incrementing an old captured seconds value. Effects with [] are mount-oriented, but development Strict Mode may perform an extra setup-cleanup-setup cycle to detect missing cleanup. Timers are not exact clocks; this is a teaching counter, not a precise stopwatch.

Test the behavior

  • Start: the number increases approximately once each second.
  • Pause: the number stops changing. Start again: it does not accelerate.
  • Reset while running: the display becomes zero and continues on the existing interval.
  • Remove the component: no interval from it remains active.

Hint 1

Starting an asynchronous operation does not pause the later console.log("B").

Hint 2

A then callback’s returned value becomes the fulfillment value of the next Promise in the chain.

Hint 3

Reference answer and explanation
// Standalone TypeScript; timer scheduling affects delay, not this log order.
function delayValue(value: number, ms: number): Promise<number> {
  return new Promise(resolve => setTimeout(() => resolve(value), ms));
}
console.log('A');
delayValue(3, 20)
  .then(value => value * 2)
  .then(value => console.log('C', value))
  .catch(error => console.error('Failed:', error));
console.log('B');
// Logs A, then B, then C 6 after the timer resolves.

The first two logs happen in the current synchronous work. The timer later resolves the Promise with 3, allowing the then callbacks to run. then returns another Promise, so a chain represents a sequence of asynchronous and synchronous transformations.

The original block callback did not return its calculation. Its next then received undefined. This is the same missing-return idea as the broken map callback, applied to a different API. catch is an error-handling extension to the deck’s basic then examples; it handles a rejection or an error thrown in the preceding chain.
